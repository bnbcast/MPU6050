What the sensor reports


        

          

            
Accelerometer

            

              Three axes in m/s². Gravity is always part of the reading, so a
              sensor lying still reports about 9.81 split across the axes by its
              tilt. Range set to ±2 g.
            

          


          

            
Gyroscope

            

              Three axes of rotation speed. The Adafruit library returns rad/s,
              and the sketch multiplies by 180/π to print °/s. Range set to ±500
              °/s. Adding the speeds up over time gives an angle that slowly
              drifts.
            

          


          

            
Temperature

            

              The chip’s own temperature in °C. Useful for spotting change, but
              it is not a calibrated room thermometer.

The sketch, in short

        

          Written for the Arduino IDE with the Adafruit MPU6050 library. Setup
          picks the ranges and filter once. The loop reads, prints, and waits.
        


        
Wire.begin(21, 22);                           // SDA = GPIO21, SCL = GPIO22
mpu.begin();                                  // default I²C address, usually 0x68
mpu.setAccelerometerRange(MPU6050_RANGE_2_G);
mpu.setGyroRange(MPU6050_RANGE_500_DEG);
mpu.setFilterBandwidth(MPU6050_BAND_21_HZ);

// in loop()
mpu.getEvent(&a, &g, &temp);
Serial.print(g.gyro.x * 180.0 / PI, 2);       // rad/s to °/s
delay(100);                                   // about 10 readings per second


        

          The 100 ms delay gives a little under 10 readings a second, since
          reading and printing take time too. The 21 Hz filter bandwidth is a
          separate setting and is not the sampling rate.
        

      


      

      

        
Project 02 · Embedded web dashboard

        
ESP32 Control Center


        

          A separate ESP32 firmware project that creates its own Wi-Fi access
          point and serves a lightweight browser dashboard. Instead of reading
          the MPU-6050, this program focuses on device health, basic GPIO
          control, and a small HTTP request history. It is designed to make
          useful device information visible without needing a desktop serial
          monitor.
        


        

          

            
What the project is for


            

              The Control Center gives a user one local page for checking the
              board’s current status and trying a simple output control. The
              ESP32 hosts the page and handles requests; the browser renders the
              returned information.
            


            
    
              
  • 
                Device health: uptime, free heap memory, CPU
                frequency, device IP, connected stations, and reset reason.
              
    • 
              
  • 
                GPIO output: a dashboard control for the LED
                connected to GPIO2.
              
    • 
              
  • 
                Request history: a rolling log of the most
                recent 40 HTTP requests.
              
    • 
              
  • 
                JSON responses: small data responses allow the
                page to update specific values without rebuilding the whole
                interface.
              
    • 
            


            

              ESP32
              Wi-Fi SoftAP
              HTTP
              JSON
              GPIO
              Embedded UI
            


            

              Separate firmware: this Control Center does not
              use the MPU-6050 sensor code above. The motion lab and Control
              Center are two distinct programs, each demonstrating a different
              ESP32 use case.

Core features


          

            

              01 / MONITOR
              
System health

              

                Surface the ESP32’s uptime, available heap, CPU clock, IP
                address, connected Wi-Fi stations, and most recent reset reason.
                These values help make basic diagnostics easier to inspect.
              

            


            

              02 / CONTROL
              
GPIO2 LED

              

                Use a small dashboard action to request an LED state change. On
                real hardware, the button needs to call the firmware endpoint
                and show the outcome returned by the ESP32.
              

            


            

              03 / OBSERVE
              
HTTP request log

              

                Keep a rolling history of the latest 40 HTTP requests. A bounded
                history is useful for recent activity without allowing the log
                to grow indefinitely.
              

            


            

              04 / CONNECT
              
Local Wi-Fi access point

              

                The ESP32 can host its own network for nearby clients. This
                makes a direct local dashboard workflow possible; the exact
                access-point name and security settings depend on the firmware.
              

            


            

              05 / EXCHANGE
              
Small JSON endpoints

              

                Structured responses give the browser predictable fields to
                display. Separate endpoints can keep status reads, LED commands,
                and request history logically distinct.
              

            


            

              06 / SEPARATE
              
Focused firmware

              

                The dashboard project is independent of the motion-sensor
                sketch. That separation keeps the responsibilities and debugging
                paths of each demonstration clear.
              

            

          

        


        

          
How the system fits together


          

            The following is the conceptual request path for the Control Center,
            rather than a claim about the exact function names in the firmware.
          


          

            

              Browser
              
                Opens the dashboard from a phone or computer connected to the
                ESP32’s local Wi-Fi network.
              
            


            

              ESP32 access point
              
                Provides the local network connection and serves the dashboard
                page.
              
            


            

              HTTP + JSON handlers
              
                Receives a status request or control action, then returns a
                response for the page to interpret.
              
            


            

              Hardware + log
              
                Reads available system information, changes GPIO2 when
                requested, and records recent HTTP activity.

What would make the project stronger


            
    
              
  • 
                Clear connection state: show loading, success,
                timeout, and error states instead of assuming every request
                works.
              
    • 
              
  • 
                Refresh strategy: update telemetry at a
                reasonable interval and stop polling when the page is hidden.
              
    • 
              
  • 
                Typed responses: keep a consistent JSON schema
                and handle missing or malformed fields safely.
              
    • 
              
  • 
                Hardware feedback: update the LED indicator
                from the device response, not only from a button click.
              
    • 
              
  • 
                Test checklist: test reconnects, repeated
                commands, unavailable endpoints, and a full request log.

Scope and safety notes


          

            

              
What this page demonstrates

              

                The preview below is a front-end mock-up: toggling the button
                changes only the local page state and appends a local demo-log
                entry. It does not connect to an ESP32, call a real API, or
                switch physical GPIO2.
              

            


            

              
Before controlling real hardware

              

                Configure the access point deliberately, use a strong network
                password, protect state-changing endpoints, validate input, and
                avoid exposing sensitive configuration or credentials in the
                request log.
              

            

          

        

      


      

      

        
Build notes · Front-end implementation

        
Technology stack & UI design system


        

          This project is a single-page, browser-based engineering demo. The
          page itself is built with native web technologies, while Three.js
          draws the interactive 3D board and the Canvas 2D API draws the
          live-style plots. The site does not use a front-end framework or a
          build pipeline.
        


        

          
            HTML5
            CSS3
            Vanilla JavaScript
            Three.js r128
            Canvas 2D
            Google Fonts
          
        


        

          

            Structure
            
HTML5

            

              Semantic page sections, headings, tables, controls, status text,
              and the project narrative. The HTML is the page source; it is not
              generated by React or another component framework.
            

          


          

            Visual system
            
Custom CSS3

            

              CSS variables, Grid, Flexbox, media queries, gradients,
              translucent panels, focus outlines, and custom responsive layouts.
              No Bootstrap or Tailwind stylesheet is used.
            

          


          

            Interactions
            
Vanilla JavaScript

            

              Direct DOM event listeners operate the rotation sliders, preset
              buttons, pointer dragging, simulated sensor updates, terminal
              output, and animation loop without a UI framework.
            

          


          

            3D rendering
            
Three.js r128

            

              A WebGL-rendered scene creates the virtual board, chip, pins, axis
              arrows, lighting, camera, and grid. It is loaded from the cdnjs
              CDN.
            

          


          

            Data plots
            
Canvas 2D API

            

              The acceleration and rotation-speed traces are drawn directly on
              canvas. There is no charting dependency such as Chart.js in this
              page.
            

          


          

            Typography
            
Google Fonts

            

              Bricolage Grotesque is used for display headings and prominent
              metrics; IBM Plex Sans handles body copy and controls.
              Terminal-style areas use a system monospace stack.

Layout, animation, and responsive behavior


          

            

              
Two-column lab

              

                The main simulator uses CSS Grid: the 3D viewport gets a wider
                column than the live readings panel. The chart area uses two
                equal columns on large screens.
              

            


            

              
Responsive breakpoints

              

                At 860px the simulator, charts, and content columns stack. At
                560px, Control Center cards, flow steps, color swatches, and
                font samples become single-column.
              

            


            

              
Motion loop

              

                requestAnimationFrame
                renders the 3D scene. A 100ms interval updates simulated
                readings and redraws the rolling plots, targeting about 10
                samples per second.
